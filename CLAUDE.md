# RoslynPad

## Project Overview

RoslynPad is a cross-platform C# editor built on Roslyn (compiler services), the Morgania editor (an Avalonia editor based on the vs-editor-api repo), and Avalonia. A single Avalonia application serves Windows, macOS, and Linux; there is no WPF code.

## Architecture

### Layer Structure (bottom to top)

```
RoslynPad.Runtime       → Injected into user scripts (.Dump() extension methods)
Morgania.Editor[.Abstractions] → The editor engine (vendored vs-editor-api) implemented on Avalonia
Morgania.CodeAnalysis.EditorFeatures → Roslyn EditorFeatures (Text+Core+CSharp) recompiled from vendor/roslyn against Morgania
Morgania.CodeAnalysis.Editor → VS-MEF composition (EditorComposition) + editor-host services (classification formats, squiggles, light bulb, glyphs, refactoring dialogs)
RoslynPad.Themes        → VS Code theme parsing
RoslynPad.Runtime.Secrets → Cross-platform secret storage
RoslynPad               → The app: entry point, Roslyn host/workspaces (Roslyn/), script compilation + execution (Build/), ViewModels/services (UI/), theme→editor mapping (Editor/)
```

The four `Morgania.*` library projects plus `RoslynPad.Themes` and `RoslynPad.Runtime.Secrets` are published as NuGet packages — each packs its `README.md`; they are listed in `docs/packages/README.md`. The demos and the app are not packable.

### Editor Integration

The app is a full editor host for the Morgania editor. Per-feature design detail and rationale live in `docs/architecture/editor-integration.md` — read the relevant section before working on one of these features. The map and the invariants that are easy to break:

- Composition: `RoslynHost` (`src/RoslynPad/Roslyn/`) builds `HostServices` over `Morgania.CodeAnalysis.Editor`'s `EditorComposition` — a single VS-MEF graph containing Roslyn Workspaces/Features, the recompiled EditorFeatures assembly, the Morgania editor, and the host services. Composition rejections are logged to `composition.log` in the app directory.
- `Morgania.CodeAnalysis.Editor` holds the editor-host services: commanding key bridge, squiggles + diagnostics tagger, light bulb, classification formats, snippets, glyphs (`Glyphs.axaml` generated by `Resources/Glyphs/generate-glyphs.py`, resolved via `ImageCatalog`), block structure guides, and refactoring dialogs (shown through the public `IDialogPresenter`; the app exports one into the main window's `DialogHost`, fallback is modal windows).
- Theming: the app's `Editor/` folder (`ThemeClassificationFormats`, `ThemeDictionary`) maps VS Code themes onto everything — classifications, editor-format-map keys (popups, find/replace, outlining, inline diagnostics, block guides, background work indicator), Dock resources (`DockTheme.axaml`), scrollbars (`ScrollBarTheme.axaml`). Invariants: the theme is authoritative — unthemed classifications get their explicit format *cleared* so they inherit through the base-type chain (no static color bleeds); the vs2019 base theme's scopes live in a separate fallback trie consulted only when the theme has no match; `ScrollBarTheme.axaml` must keep its control themes in `Styles.Resources` — assigning `Application.Resources` from XAML would replace the dictionary the `Icons` are code-merged into. Built-in themes: `src/RoslynPad.Themes/Themes/` (default `2026-light`/`2026-dark`).
- Inline diagnostics: recompiled Roslyn `InlineDiagnostics` (shims in `Morgania.CodeAnalysis.EditorFeatures/Shims/`), gated by Roslyn's `EnableInlineDiagnostics` option (off by default). Editor-UI options persist in `RoslynPad.json` via `SettingsOptionPersister` (an app-exported `IOptionPersisterProvider`; `MainViewModel` wires `Settings` into it right after creating the host). The `.editorconfig` at the documents root is attached to every project as an analyzer config document and watched; on change `RoslynHost` pushes fresh text loaders into all live workspaces — the workspace never re-reads the file on its own.
- Code folding: `StructureOutliningTaggerProvider` (Morgania.Editor) bridges `IStructureTag` → `IOutliningRegionTag`, so Roslyn's structure tagger drives folding with no Roslyn-side wiring. Collapsing elides all but the region's last character (the Avalonia text formatter can't sequence zero-length adornment runs); that character carries the clickable pill (`CollapsedRegionAdornmentProvider`), whose hover hint is upstream's live-view implementation. Ctrl/Cmd+M starts the outlining chord (+M/+L/+O) in `CommandingKeyBridge`; `CodeEditorView.NavigateToSpan` expands folds containing the target.
- `DocumentView` creates an `ITextBuffer` (CSharp content type), opens the Roslyn document over `buffer.AsTextContainer()`, and hosts the `ITextViewHost` control; workspace-applied changes round-trip through minimal buffer edits.
- Clipboard: the OS clipboard is the single source of truth (`TextViewClipboardExtensions`, Morgania.Editor). `IEditorOperations.Paste` is synchronous but Avalonia's clipboard is async-only, so every paste entry point must route through `PasteFromClipboardAsync`, which primes the view's property bag with a `PendingClipboardPaste` snapshot before the synchronous dispatch.
- Find/replace: `FindReplacePanel` (Morgania.Editor original) floats over every interactive text view; its six chords are rebindable `KeyGesture?` properties with platform defaults. Invocation is commanding (`ShowFindCommandArgs`/`ShowReplaceCommandArgs`); `CodeEditorView` is the only app type that touches the panel (pushes user keybindings per view, exposes `InvokeFindReplace`). AppKit consumes the native menu's Cmd+F/Cmd+Alt+F before Avalonia key routing, so `MainWindow` routes menu Find/Replace to the `CodeEditorView` containing the focused element. Read-only views (`ViewProhibitUserInputId`) are find-only.
- Navigation: F12/Cmd+F12 and the context menu dispatch through the commanding chain; multi-result searches surface in `StreamingFindUsagesPresenter`'s caret picker. Navigation *policy* is the app's: `src/RoslynPad/Roslyn/Navigation/` exports the navigation services at `ServiceLayer.Host`, bridged to `MainViewModel` through `NavigationBridge`/`INavigationHost` because the UI lives in the separate MEF2 container. Metadata symbols resolve Source Link/PDB sources first (`SourceLinkService`), else ILSpy decompilation (`DecompilationService`); results open as read-only tabs whose buffers register into the metadata-as-source workspace so language features keep working. Both document views host the editor through the shared `CodeEditorView`.
- Inline rename: keyboard-driven type-in-buffer rename (F2 starts, Enter commits with conflict resolution, Escape cancels) through the bridged command chain — the WPF flyout is excluded and `RenameCommandHandler` tolerates its absence. Gotcha: the package's no-op `IDocumentNavigationService` stub must export at `ServiceLayer.Editor`, because Roslyn ships a Features-layer default under the same contract.
- Trailing-expression diagnostics: `ExecutionHost` rewrites a trailing bare expression into `.Dump()` before compiling, so CS1002/CA1806 on that statement are noise; compiler errors are `NotConfigurable` (nothing can suppress them), so `TrailingExpressionDiagnosticsFilter` wraps `IDiagnosticAnalyzerService` at `ServiceLayer.Host` — the one seam every consumer (squiggles, inline diagnostics, light bulb) reads — and drops exactly those two diagnostics by span. There is no other ID-based diagnostic filtering anywhere.
- Build output pane: the bottom `ResultPane` is a `DocumentDock` (VS Code-style pill tabs, no tool chrome) with `Results`/`Build`(titled "Output")/`IL`; pre-existing saved layouts fail the `LoadDockLayout` type guard and reset once. The Restore/Compile source combo sits in the pill row via the `PaneHeader.Content` attached property (a slot in `DockTheme.axaml`'s `DocumentControl` template showing the active tab's content); saved layouts deserialize fresh `Document` objects, so `LoadDockLayout` re-applies `Title` and `PaneHeader.Content` from the XAML instances. `BuildOutputView` hosts a read-only editor over the `BuildOutput` content type (`Editor/BuildOutputClassification.cs`, VSColorOutput's line-classification scheme); colors come from the theme via `ThemeClassificationFormats.ApplyBuildOutput` (severity + `terminal.ansi*` keys, ANSI defaults registered in `VsCodeColorRegistry`). Gotcha: each type needs its colorless registration-only `ClassificationFormatDefinition` export — the classification format map only reads explicit text properties for types with an exported definition — but the definitions must stay colorless, the theme is the single source of colors. Output flows through `IExecutionHost.BuildOutputWriterFactory` (a phase-scoped `TextWriter`; creation = phase start/combo auto-switch); the view pulls incrementally via `BuildOutputDocument.ReadFrom`. Design detail: `docs/features/build-output-pane.md`.
- `Morgania.Demo.EditorFeatures` is a self-contained harness for the same integration (`--smoke` runs headless and exercises classification/completion).

### Key Classes

- `RoslynHost` - Central Roslyn services host using VS-MEF composition
- `RoslynWorkspace` - Per-document Roslyn workspace extending `Microsoft.CodeAnalysis.Workspace`
- `ExecutionHost` - Compiles and executes scripts in separate processes via JSON IPC
- `MainViewModel` - Application state and document management
- `OpenDocumentViewModel` - Individual document state, execution, NuGet integration

### Build & Restore Pipeline

- Restore is a **design-time build**: `dotnet msbuild -restore -t:Compile -p:DesignTimeBuild=true -p:SkipCompilerExecution=true`, harvesting references/analyzers/usings via `-getItem` with the JSON diverted to `output.json` by `-getResultOutputFile` — stdout stays a human-readable log that streams into the Build pane and is persisted as `output.log` in the hashed restore-cache dir for cache-hit replay. No stub source file, no `bin` output. Implicit usings come from that build, not settings; settings usings are additive.
- Scripts (`.csx`) also compile through `dotnet build`: the script csproj imports the SDK **explicitly** (`Sdk.props`/`Sdk.targets` elements) so its `CoreCompile` override — invoking `RoslynPad.BuildTasks.ScriptCompileTask` — wins over the SDK's (an `Sdk` attribute imports targets after the body, so a body-defined target would lose; `MSBuildHelper.ConvertToScriptCsproj` applies the same transform to `dotnet project convert` output). The task assembly targets netstandard2.0 (the MSBuild node runs on the runtime of whatever SDK the platform selector pins into `global.json` — older selectable SDKs mean older nodes) and ships with its Roslyn closure in `BuildTasks/` next to the app (copy targets in `Directory.Build.targets`, mirroring `runtimes/`); its `CoreCompile` honors `-p:SkipCompilerExecution` so design-time restore skips it. There is no in-process script compiler. Scripts route harvested usings through `RoslynPadImports`, since they cannot consume generated global-usings source files.
- Gotcha: the trailing-expression `.Dump()` rewrite round-trips through *text* (written to `Program.cs`/`.csx` and re-parsed), so `BuildCode.GetDumpCall` parenthesizes the receiver; and `MsbuildLogRegex` accepts both csc's `(line,col)` and the task's `(line,col,endLine,endCol)` spans.
- Reference directives: `ReferenceDirectiveHelpers` (`src/RoslynPad/Roslyn/FileBasedPrograms/`) is the only parser for `#r` and `#:package` — `ExecutionHost.ParseReferences` and the open-time `#r`→file-based migration (`DocumentView.MigrateReferenceDirectivesAsync`) both read it. The migration works off the workspace's tree rather than re-parsing, and skips any `#r` it can't express — plain assembly paths, unknown frameworks, anything after the first token — since `#:` may not follow code. `ExecutionHost` restores whenever the *set of `#:` directives* changes, not just the libraries they resolve to — `#:property`/`#:sdk` change the generated csproj without adding a reference. `#:property TargetFramework=...` (e.g. `net10.0-windows` alongside `#:property UseWindowsForms=true`) overrides the platform's TFM for the generated csproj only; the SDK dropdown and `global.json` still pin the selected SDK, which can compile an older or platform-specific framework.
- Gotcha: a setting defaulting to `true` needs `[JsonIgnore(Condition = JsonIgnoreCondition.Never)]` in `ApplicationSettings.SerializableValues` — the serializer's `WhenWritingDefault` omits `false` (the CLR default), so an opt-out would silently come back on at the next load.

## Build Commands

```bash
# Build the app
dotnet build src/RoslynPad

# Build full solution
dotnet build RoslynPad.slnx

# CI build with binary log
dotnet build -bl -c Release -m:1 RoslynPad.slnx

# Headless editor smoke test
dotnet run --project src/Morgania.Demo.EditorFeatures -- --smoke

# Morgania test suites (not in the slnx; run each the same way)
dotnet test tests/Morgania.IntellisenseTests   # also: BehaviorTests, CompositionTests, GeometryTests
```

Requires **.NET 10 SDK** (see `global.json`). Also install .NET 8 SDK for LTS library targets.

## Dependency Injection

Uses **System.Composition (MEF2)**, not Microsoft.Extensions.DependencyInjection:

```csharp
// Export service
[Export(typeof(IMyService)), Shared]
public class MyService : IMyService { }

// Constructor injection
[Export(typeof(MyViewModel)), Shared]
[method: ImportingConstructor]
public class MyViewModel(IMyService service) : NotificationObject { }
```

The `[Shared]` attribute indicates singleton lifetime.

## Key Conventions

### Naming
- Private fields: `_camelCase`
- Static fields: `s_camelCase`

### ViewModels
- Inherit from `NotificationObject` (provides `INotifyPropertyChanged`, error tracking)
- Use `SetProperty(ref field, value)` for property change notification
- Commands via `ICommandProvider.Create()` / `CreateAsync()`

### Roslyn Internal APIs

RoslynPad relies heavily on `IgnoresAccessChecksToGenerator`, which generates `[assembly: IgnoresAccessChecksTo("AssemblyName")]` attributes for Roslyn assemblies. This allows accessing non-public members and features that aren't part of Roslyn's public API surface.

**Benefits:**
- Enables consuming internal Roslyn features required for rich editor functionality
- Allows integration with internal workspace and completion APIs

**Trade-offs:**
- **Roslyn version upgrades can break the build** - internal APIs may change, be renamed, or removed between versions
- When upgrading Roslyn packages, expect to fix compilation errors where internal members have changed
- Requires careful testing after any Roslyn version bump

Relevant internal namespaces are exposed via `IgnoresAccessChecksTo` items in `Morgania.CodeAnalysis.EditorFeatures.csproj`, `Morgania.CodeAnalysis.Editor.csproj`, `Morgania.Demo.EditorFeatures.csproj`, and `RoslynPad.csproj`. The recompiled EditorFeatures assembly additionally grants `InternalsVisibleTo` to `Morgania.CodeAnalysis.Editor`, the demo host, and the app (`RoslynPad`) for the Roslyn-internal host interfaces they implement.

## Runtime Assembly

`RoslynPad.Runtime` is injected into executed user scripts. It:
- Multi-targets `net8.0;netstandard2.0` for broad compatibility
- Provides `.Dump()` extension methods
- Has no external dependencies
- Communicates with host via JSON over stdout/stdin

## Packaging & Deployment

Scripts in `deploy/` handle release packaging:

```bash
# From deploy/ directory - builds platform packages
./CreatePackages.ps1    # Runs on current OS, creates packages for that platform

# NuGet publishing (for library packages)
./PushNuGet.ps1         # Packs and pushes to nuget.org
```

**Platform Packaging** (all from `RoslynPad`):
- **Windows**: creates `.zip` + `.appx` (Microsoft Store), updates winget manifests
- **macOS**: creates a signed + notarized `.dmg` (requires `appdmg` via npm) and `.tgz`, updates the Homebrew cask
- **Linux**: creates `.tgz`

**Key Details:**
- `Common.ps1` - Shared functions, reads version from `Directory.Build.props`
- Windows packages run on Windows, macOS/Linux packages run on macOS
- `dotnet publish -r <rid>` with `ContinuousIntegrationBuild=true` for reproducible builds
- Version is centrally defined as `RoslynPadVersion` in `Directory.Build.props`; download URLs use `Get-ReleaseTag`, which drops trailing zero components to match the release tag (`22.0.0` → `22`, `21.1.0` → `21.1`)
- `deploy/brew/roslynpad.rb` is the Homebrew cask (distributed through the `roslynpad/homebrew-tap` repo). `CreatePackages.ps1` rewrites its version and both architecture hashes after notarization — stapling changes the image, so the hash must come last — and copies it into a `homebrew-tap` checkout sitting next to the repo, if there is one
